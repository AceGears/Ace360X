# PPC instruction tests on the ARM64 JIT — 2026-11-18

**What was run:** upstream Xenia Canary's `xenia-cpu-ppc-tests --cpu=a64` (hand-written
`instr_*.s` tests and generated `instr__gen_*.s` tests, assembled with patched binutils
2.24). Expected values come from upstream's test files, which record real Xbox 360 results.

**Where:** GitHub Actions `ubuntu-24.04-arm` runner (real ARM64 CPU, Linux), clang-20.
Workflow: `.github/workflows/ppc-tests.yml`. This is a host test. It does not run on an
Android device and says nothing about GPU, kernel or game compatibility.

**Upstream base:** xenia-canary `28bc50db` plus Ace360X patches 0001–0009, then 0010–0012.

Before 0010, every integer, branch, load/store, logical and integer-vector test passed. All

The test job is now a CI gate: any failing case fails the workflow.

## What was wrong, and the fix

| Class | Affected instructions (failing cases before) | Cause | Fix |
|---|---|---|---|
| Negated multiply-add | `vnmsubfp` (13,655), `fnmsub`/`fnmadd` (2,040 each), `fnmsubs`/`fnmadds` (1,448 each), `vnmsubfp128` | a64 ignored the HIR `ARITHMETIC_NEGATE_RESULT` flag, so it returned the un-negated value | 0010 negates after rounding, so −(+0) gives −0. NaN signs are left alone. |
| Default NaN sign | `fadd`/`fsub`/`fmul`/`fdiv`(s), `fmadd`/`fmsub`(s) | An invalid operation (∞×0, ∞−∞) gave `0xFFF8…`/`0xFFC00000`; PowerPC gives positive `0x7FF8…`/`0x7FC00000` | 0010 |
| Multiply-add NaN priority | `vmaddfp` (1,012), scalar FMA | The first NaN was checked in the order A, C, B; PowerISA's order is A, B, C | 0010 |
| `vmaxfp`/`vminfp` NaN choice | 37 each | NEON prefers a signalling NaN; PowerPC returns vA if it is NaN, else vB, quieted | 0010 |
| Estimates | `vlogefp`, `vrefp`, `fres`, `vexptefp` (+128 forms) | Host `log2`/`exp2`/division instead of the console's estimates | 0011 calls upstream's shared bit-exact `ppc::Estimate*` |
| Dot product rounding | `vmsum3fp128`, `vmsum4fp128` (1 each) | Rounded to nearest; the console's result is closer to truncation | 0012, the same as upstream x64's default path (about 97 % console-exact per upstream) |

## Limits of this evidence

- The tests cover single instructions. Passing them does not show that any game boots.
- 0011 replaces inline arithmetic with a native helper call per estimate instruction.
  Its speed cost has not been measured.
- The vmsum change matches upstream x64's default "fast" model, not the exact model.
- Nothing here ran on a phone. Snapdragon cores implement the same ARMv8 FP semantics, but
  that is an expectation and has not been measured.
